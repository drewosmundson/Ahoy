All gameplay comes from these injected components, systems, and resources from the games import.
The overall goal of this archetecture was strict adhearence to the DRY principal as well as creating a framework that would trivialize modifications and extendtions.
I stove towards this for a few weeks while thinking about how adding new features on the game layer can be done without having to worry of the domino effect of implications on the engine for game changes
The process of working through this then created an explosion of reusablilty that eventually lead me to creating a modular game agnostic engine.

It was not somthing that I had set out to do. I wanted to make games, but the discovery that emerged from this gardener style of design, implementation, and redesign that scratched my creative + academic itch.
I learned more along the way here of what makes good software Archetecture by rengineer from monolith to systems that help themselves and when to create meaningful self imposed limitations and bounderies that do not constrain potential but insead act as guide rails for an ever growing tree of complexity that grows linearly with features and whos progress time taken scaling with feature size can better be predicted and
The test and retest of what really makes reusable software and most importenty lean when to ask why and when to walk back on overengineering as pointed out by my friend
